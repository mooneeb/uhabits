# Fork documentation and PWA hosting

Researched on 2026-10-05. Provider limits and Google policies can change;
recheck the linked primary sources before a future deployment.

## Documentation guidance and requirements

GitHub recommends that a README explain what the project does, why it is
useful, how to start, where to get help, and who maintains it. GitHub also
recommends relative links for repository documents. These are platform
recommendations, rather than a mandatory README format or an industry
certification. [GitHub README guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)

A fork has its own settings, issues, releases, and collaboration space,
while retaining its connection to upstream. The README should therefore
identify the original project and explain this fork's differences and
support channel early. This is our recommendation based on GitHub's fork
model. [GitHub forks reference](https://docs.github.com/en/pull-requests/reference/forks)

Diátaxis separates tutorials, task-oriented how-to guides, reference, and
explanation. It is a practical documentation framework, not an ISO standard.
For this repository, keep getting started and hosting instructions separate
from architecture decisions and historical release evidence.
[Diátaxis introduction](https://diataxis.fr/start-here/)

The repository's [license](../../LICENSE.txt) is GPLv3. Its actual license
terms are requirements, unlike the writing recommendations above: retain
license and copyright notices, prominently identify modifications with a
relevant date, and meet the corresponding-source conditions when distributing
compiled releases. Preserve upstream attribution and link each release to its
exact source revision and build instructions. This note summarizes the relevant
terms; the license text controls. [GPLv3, sections 4–6](https://www.gnu.org/licenses/gpl.en.html)

Recommended reader-facing structure:

- **README:** personal fork status, upstream attribution, concrete differences,
  Android download, how to run your own PWA, support and license.
- **Getting started:** everyday tracking, installing the PWA, optional Drive
  synchronization, browser reconnects, and backups.
- **Hosting:** a short provider choice, then Cloudflare Pages, Docker, and
  Kubernetes steps with placeholders and expected results.
- **Google setup:** project, web origin, Android signing identity, test-user
  access, and limitations of the maintainer's prebuilt APK.
- **Reference:** build and release commands, architecture, and validation
  evidence; clearly distinguish observed checks from claims about all users.

Avoid advertising a maintainer deployment as a public service. Use example
addresses and reader-owned infrastructure values. A public repository or a
downloadable APK does not establish that arbitrary users can use the
maintainer's Google configuration.

## What the code requires from hosting

Inspection of [PWA packaging](../../scripts/package-pwa.py),
[web build](../../uhabits-web/build.gradle.kts),
[Drive transport](../../uhabits-web/src/jsMain/resources/app/drive.mjs),
[browser storage](../../uhabits-web/src/jsMain/resources/app/storage.mjs), and
[service worker](../../uhabits-web/src/jsMain/resources/app/sw.js) shows that
the deployed website is static HTML, JavaScript, CSS, images, migrations, and
WebAssembly. Habit storage and reconciliation run in the clients; the browser
contacts Google directly. A custom synchronization server, server-side Google
secret, home server, container, and Kubernetes cluster are unnecessary for
static hosting. This conclusion follows from the inspected implementation.

Measured release 20311's `site/` directory locally: 32 files totaling
5,768,138 bytes; its largest file is `loop-core.js` at 4,952,637 bytes. Those
measurements are evidence for this release, not a limit guaranteed for future
builds. Upload the contents of `site/`, preserving `app/`, `session/`, `update/`,
and `loop-core.js` as siblings. Open `/app/`; the release currently removes the
development root `index.html` and nginx supplies its root redirect.

Use HTTPS, serve files with their correct content types, preserve relative
paths, and avoid long-lived browser caching of shell files. Preserve the
service-worker cache version generated by packaging. Set a deployment's OAuth
client before packaging so changed configuration produces a new shell version.
The checked-in [nginx configuration](../../deploy/nginx.conf) is the reference
for the application's existing response headers. These recommendations follow
from the repository's loading and offline-update behavior.

## No-cost choices

| Provider | Current no-cost offer | Practical fit |
| --- | --- | --- |
| Cloudflare Pages | Static asset requests are free and unlimited. Free sites allow 20,000 files and 25 MiB per file; dashboard drag-and-drop allows 1,000 files. Git builds allow 500 builds/month. | Recommended first option for this small static PWA: upload prebuilt files and use the supplied `pages.dev` address. |
| GitHub Pages | GitHub Free supports Pages from public repositories. Published sites are limited to 1 GB, with a soft 100 GB/month bandwidth limit. | Suitable alternative, subject to Pages usage rules; a project site introduces a repository path. |
| Firebase Hosting, Spark | Hosting storage is free up to 10 GB; transfer is free up to 10 GB/month. On Spark, exceeding transfer disables the site after a grace period until the next month. | Compatible alternative with explicit usage caps; deploy only Hosting, without adding a database or server. |

Sources: [Cloudflare static pricing](https://developers.cloudflare.com/pages/functions/pricing/),
[Cloudflare limits](https://developers.cloudflare.com/pages/platform/limits/),
[Cloudflare upload limits](https://developers.cloudflare.com/pages/get-started/direct-upload/),
[GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits),
[Firebase Hosting quotas](https://firebase.google.com/docs/hosting/usage-quotas-pricing).

### Recommended: Cloudflare Pages

Direct Upload accepts prebuilt assets through the dashboard or Wrangler, serves
them from `<project>.pages.dev`, and supports later production deployments.
A custom domain is optional. Direct Upload projects cannot later switch to Git
integration, so choose that workflow deliberately.
[Cloudflare Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)

Cloudflare serves matching directory index pages, supplies content-type and
security headers, and normally uses browser cache revalidation. Custom response
headers can be supplied through a `_headers` file. For this app, explicitly
document `/app/` as its launch address; optionally add a root redirect rather
than relying on a missing root page or an unrelated SPA fallback.
[Cloudflare serving behavior](https://developers.cloudflare.com/pages/configuration/serving-pages/),
[Cloudflare headers](https://developers.cloudflare.com/pages/configuration/headers/)

Hosting privacy is separate from Google authorization. Pages deployment URLs
are public by default. The dashboard's preview Access toggle protects preview
deployments, **not** the production `pages.dev` address or custom domain. If a
reader wants a private site, protect the production address explicitly and
include every alternative hostname in the access policy.
[Cloudflare preview access](https://developers.cloudflare.com/pages/configuration/preview-deployments/),
[Cloudflare production Access setup](https://developers.cloudflare.com/pages/platform/known-issues/)

### GitHub Pages

A user site is rooted at `https://<owner>.github.io`; a project site is rooted
at `https://<owner>.github.io/<repository>`. The generated domain avoids buying
a domain. The app's relative resource, manifest, and worker paths suggest a
project site can preserve this layout under `<repository>/app/`, but that
specific provider/path combination has not been accepted through live UI
checks. Do not describe it as validated without checking install, offline
reopen, temporary mode, and update on that actual URL.
[GitHub site types](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

GitHub Pages disallows hosting a commercial SaaS or sites primarily facilitating
commercial transactions, and cautions against sensitive transactions such as
password collection. This personal app delegates Google consent to Google's
UI, but a future commercial service needs a fresh policy assessment.
[GitHub Pages usage rules](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

### Firebase Hosting

Firebase Hosting supplies HTTPS, a CDN, and free `web.app` and `firebaseapp.com`
subdomains. Its CLI supports static deployment and rollback. Those features
fit this PWA's architecture; actual Google consent and offline behavior on a
Firebase deployment remain unverified here.
[Firebase Hosting overview](https://firebase.google.com/docs/hosting)

## Google configuration remains a separate step

The web OAuth client must authorize the exact origin used for hosting, for
example `https://your-project.pages.dev`, without `/app/`. Google's browser
setup uses a public client ID; its client secret is only needed for server-side
operations and must not be placed in this static website.
[Google browser client setup](https://developers.google.com/identity/oauth2/web/guides/get-google-api-clientid)

The app requests `drive.appdata`, which Google classifies as non-sensitive.
Drive's hidden application-data folder is accessible only to the creating
application, is separate from visible Drive backup folders, and cannot share
its files with other apps.
[Google application-data storage](https://developers.google.com/workspace/drive/api/guides/appdata)

The current clients send JSON change packs without implementing client-side
encryption in the transport; hidden application-data storage should not be
presented as end-to-end encryption.
[Current Drive transport](../../uhabits-web/src/jsMain/resources/app/drive.mjs)

Google models related web and Android clients as components of one application
under one Google Cloud project. Configure both clients in the same reader-owned
project for an independently operated Android/PWA pair. Combined with Drive's
application-specific storage, this supports the practical warning that a PWA
client from another project should not be assumed to synchronize with the
maintainer's APK. Use a matching Android build/signing identity and validate
the pair. The storage interoperability conclusion is an inference from Google's
project model and application-data isolation.
[Google cross-client identity](https://developers.google.com/identity/protocols/oauth2/cross-client-identity),
[Google application-data isolation](https://developers.google.com/workspace/drive/api/guides/appdata)

An Android OAuth client is registered with the Android package name and the
SHA-1 fingerprint of the APK's signing certificate. Google recommends using
the publisher's own private signing key for a production APK. A generic setup
guide should show how to obtain the reader's fingerprint rather than copying
the maintainer's certificate identity.
[Google OAuth client types](https://support.google.com/cloud/answer/15549257)

An external project in **Testing** allows only listed test users, up to 100;
consent authorizations expire after seven days for scopes beyond basic identity.
Publishing the app changes its audience, and brand/scope verification depends
on Google's criteria. Do not describe personal consent configuration as open
to everyone, or claim that non-sensitive `drive.appdata` requires restricted
scope verification. Scope classification, audience, and verification are
separate concepts.
[Google app audience](https://support.google.com/cloud/answer/15549945),
[Google OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies)

The browser uses Google's access-token flow and stores authorization in memory.
Google requires obtaining a new valid token when one expires; automatic refresh
is not part of the browser token flow. Reconnecting after reopening is an
expected product limitation that should be stated in user instructions.
[Google web authorization](https://developers.google.com/identity/oauth2/web/guides/overview),
[current browser implementation](../../uhabits-web/src/jsMain/resources/app/app.mjs)

## Recommended documentation decision

Offer Cloudflare Pages as the simplest no-cost hosting route. Retain clear
Docker and Kubernetes instructions for readers who prefer infrastructure they
control. Distinguish tested local/container packaging from untested live
provider deployments. Keep Google project setup shared across all hosting
guides, and explain that moving to a different browser origin creates separate
local browser storage: synchronize or export first, then reconnect at the new
origin using the same intended application project.
